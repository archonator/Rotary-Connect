# Architecture

## Overview

Rotary Connect is a serverless, privacy-first messenger built on [Nostr](https://github.com/nostr-protocol/nostr) and shipped as a Progressive Web App. All state lives on the user's device, encrypted at rest with a PIN-derived key. Messages travel through a federated network of public Nostr relays — and, where possible, directly peer-to-peer over WebRTC.

```
┌────────────────────────────────────────────────────────────────────┐
│                          Browser (PWA)                             │
│                                                                    │
│   React UI  →  Zustand Store  →  Vault (AES-GCM)  →  localStorage │
│                       ↕                                            │
│                  lib/nostr.ts  ←→  Nostr Relays (WSS)              │
│                       ↕                                            │
│              lib/webrtc/PeerManager  ←→  Direct P2P data channels  │
└────────────────────────────────────────────────────────────────────┘
```

Three independent layers:

1. **Vault** — local encryption at rest (PIN → KEK → DEK → all sensitive localStorage values).
2. **Nostr** — publish/subscribe over WebSocket, used both for application messages (NIP-04, NIP-17) and as a signaling channel for WebRTC.
3. **WebRTC** — when both sides are online, messages flow directly P2P over an encrypted data channel; relays serve as fallback.

## App phase machine

`App.tsx` runs a small state machine on startup:

```
splash (2.8s)
   │
   ├── vault-unlock     existing encrypted vault → ask for PIN
   ├── vault-setup      existing plaintext data → migrate + set PIN
   └── setup            no data → create or restore identity
                            │
                            └── pin-after-setup → ready
```

Once `ready`, the main UI mounts: Sidebar + ChatArea + modals.

## Local-only data: the vault

All sensitive data in `localStorage` is encrypted before it lands on disk.

```
PIN ─── PBKDF2(SHA-256, 600 000 iter, 32-byte salt) ───► KEK
KEK ─── AES-256-GCM ─── encrypts ───► DEK   (random 256-bit, stored encrypted)
DEK ─── imported as non-extractable CryptoKey ───► encrypts each value
```

- **KEK** (Key Encryption Key) is derived from the PIN at unlock time.
- **DEK** (Data Encryption Key) is generated once at vault creation, wrapped by the KEK, and held in memory as a non-extractable WebCrypto key.
- Changing the PIN re-wraps the DEK only — no bulk data re-encryption.
- Encrypted values are stored as `v1:<base64-iv>.<base64-ciphertext>`.
- Verification token (`alina-vault-ok`) lets `unlockVault()` detect a wrong PIN via AES-GCM auth-tag failure without leaking timing.

Encrypted localStorage keys (handled by `src/lib/storage.ts`):

| Key | Content |
|---|---|
| `alina_identity` | `{ privkey: number[], pubkey: string, name: string }` |
| `alina_contacts` | `Record<pubkey, { pubkey, name }>` |
| `alina_rooms` | `Record<hash, { name, hash, members: string[] }>` |
| `alina_messages` | `Record<chatId, Message[]>` |
| `alina_unread` | `Record<chatId, number>` |
| `alina_offline_queue` | `QueuedMessage[]` (compose-while-offline) |

Non-sensitive keys remain plaintext: `rc-lang`, `alina-autotranslate`, `alina-allow-external-translate`, `alina-pwa-dismissed`, `alina-webrtc-mode`, `alina-turn-*`, `alina_pin_attempts`, `alina_logs`, `alina-tr:*` (translation cache).

> The `alina_*` / `alina-*` prefixes are historical leftovers from the project's previous name. They are stable on-disk and intentionally not renamed to avoid wiping existing user data; new keys use the `rc-` prefix.

## Identity & keys

Rotary Connect uses secp256k1 key pairs (the same curve as Bitcoin), provided by `nostr-tools`.

```
generateSecretKey()   →  privkey: Uint8Array (32 bytes)
getPublicKey(privkey) →  pubkey: hex string (64 chars)
```

Keys are encoded using NIP-19 (bech32):
- `nsec1…` — private key (import/export, shown as "secret key" in the UI)
- `npub1…` — public key (shareable, shown as "sharing code")

The private key never leaves the device. It is stored vault-encrypted in `localStorage` as a JSON array of bytes and rebuilt as a `Uint8Array` after vault unlock.

## Nostr protocol usage

### Event kinds

| Kind | Purpose | Spec |
|---|---|---|
| 4 | Direct message (E2E encrypted) | NIP-04 |
| 13 | Seal (NIP-17, encrypted rumor) | NIP-17 |
| 14 | Chat-message rumor (inside a Seal) | NIP-17 |
| 42 | Room presence / join announcement (non-sensitive) | NIP-28 (re-purposed) |
| 1059 | Gift Wrap (NIP-17, encrypted seal with ephemeral key) | NIP-17 |
| 10051 | Key migration / rotation event (custom) | — |
| 10420 | Invite code (custom) | — |
| 25050 | WebRTC signaling (ephemeral, NIP-04 encrypted) | custom |

### Relays

Default set (configurable in `src/lib/constants.ts`):

```
wss://relay.damus.io
wss://nos.lol
wss://nostr.mom
wss://nostr.wine
wss://purplepag.es
wss://relay.primal.net
wss://relay.nostr.bg
```

Each relay has its own `WebSocket` and exponential-backoff reconnection (`5s → 10s → 20s → … → 120s`). The live relay count drives a red/yellow/green status dot in the sidebar.

### Subscriptions (per relay, after connect)

```
REQ dm-sub    { kinds: [4],     "#p": [myPubkey], limit: 100 }     // NIP-04 DMs to me
REQ gw-sub    { kinds: [1059],  "#p": [myPubkey], limit: 200 }     // NIP-17 gift wraps to me
REQ sig-sub   { kinds: [25050], "#p": [myPubkey], limit: 20,
                                  since: now - 60 }                // WebRTC signals to me
REQ mig-sub   { kinds: [10051], authors: [...contacts], limit: 50 }// Contact key rotations
REQ room-sub  { kinds: [42],    "#e": [...roomHashes], limit: 200 }// Room presence
```

### Incoming dispatch

`src/lib/nostr.ts → handleRelayMessage`:

```
EVENT
 ├─ subId is a pending invite lookup → resolve invite promise
 ├─ kind 1059 (gift wrap) → unwrap + unseal → store room message
 ├─ kind 25050 (signal)   → NIP-04 decrypt → PeerManager.handleSignal
 ├─ verifyEvent fails     → drop
 ├─ kind 4   (DM)         → NIP-04 decrypt → store message
 ├─ kind 42  (presence)   → learn room member
 └─ kind 10051 (migrate)  → verifyMigrationEvent → notify (callback)
```

## Direct messages (NIP-04)

DMs use ECDH shared-secret derivation + AES-256-CBC.

### Send flow

```
ChatInput.publishMessage
  ├── if WebRTC peer is connected → send directly over data channel + return
  └── else
        publishDM(privkey, myPubkey, recipientPubkey, { type, content, ttl? })
          → encryptDM()           // nip04.encrypt
          → createSignedEvent()   // kind 4, tags: [["p", recipientPubkey]]
          → publishToRelays()
```

Outgoing messages are added locally with `status: 'sending'` and updated to `'sent'` or `'failed'` once publish resolves; failed messages get a retry button. If the device is offline or no relays are connected, the message goes into the offline queue.

### Receive flow

```
handleDM(event)
  → decryptDM(privkey, senderPubkey, content)
  → reject if > 1 MB
  → JSON.parse({ type, content, ttl? })
  → drop already-expired messages (clock skew safety)
  → onMessageCallback("dm:" + senderPubkey, msg)
```

Message envelope (after decryption):

```json
{ "type": "text" | "image" | "location", "content": "...", "ttl": 3600 }
```

## Group rooms (NIP-17)

Group rooms are end-to-end encrypted — every message is sealed and gift-wrapped per recipient.

### Room identity

The room name is hashed (case-folded) to produce a deterministic identifier:

```
roomHash = SHA-256("alina-room-v1:" + name.toLowerCase())  // 64 hex chars
```

No server-side room creation is needed — the hash is the room. Anyone who enters the same name lands in the same chat.

### Member discovery

When a client joins or sends a message it publishes a non-sensitive **kind 42 presence event** (just its name) tagged with the room hash. Other members subscribe to that and learn the membership list. Encrypted chat events are then gift-wrapped to every known member.

### Send flow

```
publishRoomMessage(privkey, myPubkey, roomHash, { type, content, name })
  ├── build kind-14 rumor (unsigned chat-message)
  ├── for each known room member ≠ self:
  │     seal      = createSeal(myPriv, myPub, member, rumor)         // kind 13
  │     giftWrap  = createGiftWrap(member, seal)                     // kind 1059
  │     publishToRelays(giftWrap)
  └── publishRoomPresence(...)   // so future members can find us
```

### Receive flow

```
handleGiftWrap(event)
  → unwrapGiftWrap → seal      (NIP-44 decrypt with own privkey)
  → unsealRumor    → rumor     (NIP-44 decrypt with seal.pubkey)
  → reject if > 1 MB or wrong kind
  → addRoomMember(roomHash, senderPubkey)
  → onMessageCallback("room:" + roomHash, msg)
```

> **Caveat:** because gift wraps target only known members, a brand-new member who hasn't yet sent a presence event won't receive history until they do. This is a fundamental property of NIP-17 rooms without a coordinator.

## Invite codes

Adding a contact via 6-digit one-time code (Nostr kind 10420):

1. **Inviter** publishes a kind-10420 event:
   ```
   tags:    [["t", SHA-256("alina-invite-v1:" + code)],
             ["expiration", unixTs + 600]]
   content: JSON.stringify({ name: "Alice" })
   ```
   The plaintext code is never published — only its SHA-256 hash.

2. **Recipient** queries by hash:
   ```
   REQ invite-<random> {
     kinds: [10420],
     "#t": [SHA-256("alina-invite-v1:" + code)],
     since: now - 600,
     limit: 5
   }
   ```
   On match, the inviter's pubkey + name are returned (≤ 8 s timeout). Codes expire after 600 s.

## WebRTC P2P

For direct (1-on-1) conversations, Rotary Connect attempts a direct WebRTC connection between contacts. When the data channel is open, messages bypass relays entirely.

### Modes (Settings)

| Mode | Behaviour |
|---|---|
| **Standard** | STUN-only, allows direct P2P. Peers see each other's IP. |
| **Private** | TURN-only (`iceTransportPolicy: 'relay'`). User-supplied TURN credentials. Hides IPs. |

### Signaling

WebRTC SDP offers/answers and ICE candidates are NIP-04 encrypted and sent as ephemeral kind-25050 Nostr events. The receiver discards anything older than 60 s. No third-party signaling server is required.

### Negotiation

`PeerManager.handleOffer` implements **perfect-negotiation**: when both peers send offers simultaneously (glare), the peer with the lexicographically smaller pubkey is "polite" and rolls back its offer; the other accepts incoming. ICE candidates are buffered until the remote description is set.

### Connection lifecycle

```
connectToPeer(pubkey)
  → createPeerEntry → RTCPeerConnection
  → createDataChannel('alina-msg', { ordered: true })
  → createOffer → setLocalDescription → onSignalOut(offer)

(remote sends answer + ICE candidates via Nostr)

  → setRemoteDescription
  → flush buffered ICE
  → datachannel.onopen → state = 'connected'
```

When connection state goes to `disconnected` / `closed` / `failed`, the entry is cleaned up after 10 s (giving a chance to recover). The store mirrors per-peer states (`disconnected | connecting | connected | failed`) for UI indicators.

## Key rotation (NIP-style migration, kind 10051)

Users can rotate their Nostr identity from Settings → Rotate Key.

```
old-key   signs a kind-10051 event:
   tags:    [["p", newPubkey], ["alt", "Key migration event"]]
   content: { newPubkey, crossSignature, message }

cross-signature is itself a kind-10051 event signed by the **new** key:
   content: "migrate:<oldPubkey>:<ts>"
   tags:    [["proof", oldPubkey]]
```

Both signatures are required — old key proves it authorised the migration; new key proves it controls the new identity. Contacts are also notified via NIP-04 DM from the old key. Verification (`verifyMigrationEvent`) checks both signatures and the `proof` linkage.

> The receiver-side wiring (`setOnMigration` callback) is currently a no-op. Receivers verify and log migration events but do not yet auto-update their contact's pubkey — that's tracked in [ROADMAP.md](./ROADMAP.md).

## State management

A single Zustand store (`src/store/useStore.ts`) holds all app state:

| Domain | Key state | Persistence |
|---|---|---|
| Identity | `identity` (privkey, pubkey, name) | vault-encrypted localStorage |
| Contacts | `contacts: Record<pubkey, Contact>` | vault-encrypted localStorage |
| Rooms | `rooms: Record<hash, Room>` (incl. `members: string[]`) | vault-encrypted localStorage |
| Messages | `messages: Record<chatId, Message[]>` | vault-encrypted localStorage |
| Unread | `unread: Record<chatId, number>` | vault-encrypted localStorage |
| Offline queue | (in `lib/offlineQueue.ts`) | vault-encrypted localStorage |
| Peer states | `peerStates: Record<pubkey, PeerState>` | in-memory only |
| Relay | `relayCount` | in-memory only |
| Language | `lang: 'de' \| 'en'` | localStorage `rc-lang` |
| Auto-translate | `autoTranslate`, `allowExternalTranslation` | localStorage |
| UI | `openModal`, `sidebarOpen`, `statusMessage` | in-memory only |

### Chat ID convention

```
"dm:"   + pubkey    →  direct-message thread
"room:" + roomHash  →  group room thread
```

### Message deduplication

`addMessage` deduplicates by `eventId` first, falling back to `(ts, pubkey)` for locally-created messages without a Nostr event ID.

### Message limit

Each chat keeps at most `MAX_MESSAGES_PER_CHAT = 200` messages. Older messages are trimmed from the front.

### Ephemeral messages

A message can carry a TTL (seconds). When set, the local `expiresAt` is computed and `useEphemeralCleanup` (1s interval) prunes expired messages from the store and from disk. The TTL also rides on the wire payload so receivers honour it too.

## Internationalisation (i18n)

Currently shipping languages: **German (`de`)** and **English (`en`)**.

- `src/lib/i18n.ts` — flat key-value dictionaries. Keys are typed (`TKey`), so missing translations are caught at compile time.
- `src/hooks/useT.ts` — React hook returning `t(key, params?)`. Subscribes to `lang` from the store; all components re-render on language change.
- Parameter interpolation uses `{placeholder}` syntax: `t('sidebar.relays', { n: '3', total: '7' })`.

Language preference is stored in `localStorage` under `rc-lang` and defaults to `'en'`.

> Russian support has been an aspiration but is not currently shipped. Tracked in [ROADMAP.md](./ROADMAP.md).

## Auto-translation

Incoming text messages can be translated client-side after NIP-04/NIP-17 decryption. **Decrypted plaintext never leaves the device unless the user explicitly opts in to the external fallback.**

```
translate(text, targetLang, allowExternal)
  1. localStorage cache (`alina-tr:<djb2(text)>:<lang>`)
  2. detectLang(text)
       a. Chrome AI Language Detector API (Chrome 127+, offline)
       b. Script heuristics (Cyrillic, CJK, Arabic …) as fallback
  3. if detectedLang === targetLang → skip
  4. translateChromeAI(text, from, to)        // fully offline, no network
     OR (if allowExternal)
     translateMyMemory(text, from, to)        // free public API, 8s timeout
  5. cache result
```

The "Allow external translation" toggle in Settings gates step 4-fallback to MyMemory. Default: off.

`@khmyznikov/pwa-install` wraps platform install dialogs:

- **iOS Safari**: step-by-step guide (Share → Add to Home Screen), since iOS never fires `beforeinstallprompt`.
- **Android Chrome / Desktop**: native install dialog wrapper.

`src/lib/offlineQueue.ts` queues messages when `navigator.onLine === false` or no relays are connected. The queue is encrypted in the vault and flushed on the `online` event (and 3 s after the relay layer wires up).

## Security model

| Concern | Mitigation |
|---|---|
| Private key exposure | Vault-encrypted at rest; never transmitted; only revealed in Settings (and only after explicit "show key" tap) |
| Local-device attack | PIN gate with PBKDF2-600k + AES-GCM; 5 attempts → 60s lockout (UI hint, not cryptographic) |
| DM confidentiality | NIP-04: ECDH + AES-256-CBC; relays see only ciphertext |
| Group room confidentiality | NIP-17: per-recipient gift-wrapped Seal; ephemeral wrap key |
| Metadata privacy | Gift-wrap timestamps are randomized; signaling events are NIP-04 encrypted |
| Invite-code brute force | 10⁶ codes, SHA-256 hashed on relays, 600s expiry |
| XSS via message content | React renders all content as text — no `dangerouslySetInnerHTML` |
| Image-payload size | Compressed to ≤ 500 KB base64 client-side before sending |
| Build dependency CVE | `serialize-javascript` pinned to `≥7.0.5` via npm `overrides` |
| Replay of stale signaling | Receiver drops kind-25050 events older than 60s |
| External translation leak | Off by default; user-toggleable in Settings |

For known limitations and planned hardening, see [ROADMAP.md](./ROADMAP.md).
